# Interfold (Gnosis Guild): модульная арифметика на подсказках — первый проход

Цель выбрана по `docs/research/noir-bug-directions/real_world_noir_targets.md`
(пункт 2 рейтинга: «unaudited + hint-heavy + holds value»). Опубликованные
аудиты Interfold (Zenith, 2026) прямо говорят: «It covers no Rust and no
circuits». Как выяснилось позже, схемы всё же проходили внешний аудит
с неопубликованным отчётом (см. «Поправку» ниже). Дополнительный
практический довод: Interfold закрепляет `nargo v1.0.0-beta.26`
(`crates/zk-prover/Cargo.toml`), то есть **ровно ту ревизию ACIR (`40d6574`),
на которой собран адаптер** — артефакты читаются без пересборки компилятора.

Срез: `gnosisguild/interfold` @ `64292e8f5da6eeb7de78c3f904723f828397faf8`
(2026-10-06), пресет по умолчанию `insecure-512`, комитет `minimum` (N=3, T=1).

## Итог в одну строку

Уязвимости в боевых схемах **нет**. Новое — только мелкое расхождение кода с
документацией в `ModU64::sub` и `ModU64::inv_mod`: они не ограничивают результат
интервалом `[0, m)`, хотя обещают `(lhs - rhs) mod m` / `val^(-1) mod m`.
Ни одна боевая схема их не вызывает, так что это замечание по hardening.
C7 (`decrypted_shares_aggregation`) вручную проверен и корректен; это
подтверждает исправление IF-012, которое авторы внесли за 3 дня до нашего
среза. Сканер на C7 вердикта не даёт.

## Поправка после сверки с репозиторием Interfold

Первая версия этого отчёта переоценила находку. При сверке с их внутренней
документацией выяснилось следующее.

- **Схемы проходили внешний аудит.** Опубликованные PDF Zenith касаются только
  контрактов, отсюда и фраза «covers no circuits» в заметке
  `real_world_noir_targets.md`. Но в `agent/flow-trace/00_INDEX.md` (раздел
  «Circuit Audit Remediations», строки 209–225) лежит таблица IF-001…IF-014:
  находки по схемам, все исправлены, с пометкой «Found by external audit».
  Сам отчёт этого аудита не опубликован. Значит, тезис «схемы не аудированы»
  в research_notes неточен.
- **Класс дефекта авторам хорошо знаком.** IF-001 — неограниченная подсказка
  ровно в `ModU64::div_mod`. IF-012 — неограниченные частные в C7. Коммит
  `c98b0d1c` (2026-10-03, «bound openings, quotients and VK trees») добавил
  `reduce_mod_bounded` и `inv_mod_bounded`, и именно их мы проверяли в C7.
- **Про `ModU128` авторы всё знают и пишут об этом прямо.**
  `agent/invariants/02_CRYPTO_CIRCUITS.md:240-250` и doc-комментарий
  `ModU128::inv_mod` («Do not use this on a value a prover controls») говорят:
  весь `ModU128` (`add`, `sub`, `mul_mod`, `div_mod`, `inv_mod`) небезопасен для
  значений, которые выбирает доказывающий, и используется только на константах
  в `bin/config`. Поэтому `ModU128::sub` и `ModU128::inv_mod` **не находка**.
- **Не задокументированы только `ModU64::sub` и `ModU64::inv_mod`.** `ModU64` —
  тот модуль, который считается безопасным для подсказок: на нём работают C2,
  C3 и C5. Его `reduce_mod`/`mul_mod` зажимают остаток `< m`, а `sub` и
  `inv_mod` — нет. Вызовов этих двух функций вне тестов нет.

Что из этого следует. Баг — в том смысле, что функция не выполняет
собственный doc-комментарий, и соседние функции того же типа это ограничение
соблюдают. Но это не уязвимость: эксплуатировать нечего, пока функцию никто не
вызывает. Задумано ли так — могут сказать только авторы. Против замысла
говорит то, что для `ModU128` они ту же особенность задокументировали, а для
`ModU64` нет.

## 1. Инвентаризация подсказок

`nargo info` по всем пакетам `bin/threshold` и `bin/dkg`:

| схема | ACIR | Brillig | откуда подсказки |
|---|---:|---:|---|
| threshold/decrypted_shares_aggregation (C7) | 5179 | 1799 | `reduce_mod_bounded`, `inv_mod_bounded`, `divide_big_hint` (bignum) |
| threshold/pk_aggregation (C5) | 11963 | 24 | `ModU64::assert_zero_mod_bounded` |
| threshold/share_decryption (C6) | 20893 | 8 | — (директивы компилятора) |
| threshold/pk_generation, ct0, ct1, user_data_encryption | 11–26228 | 0 | нет |
| dkg/sk_share_computation (C2a) | 18130 | 24 | `ModU64::assert_zero_mod` |
| dkg/e_sm_share_computation (C2b) | 34721 | 41 | `ModU64::assert_zero_mod` |
| dkg/share_decryption (C4) | 11617 | 48 | `centered_mod_bounded` |
| dkg/share_encryption (C3) | 33553 | 51 | `ModU64::mul_mod` |
| dkg/pk (C0) | 344 | 0 | нет |

Явные `unsafe { … }` вне тестов есть только в `math/modulo/*` и в C7.

Попутно проверено, что неявная проверка диапазона на возврате `u64` из
unconstrained-функции действительно вставляется (`BLACKBOX::RANGE w, bits: 64`
сразу после `BRILLIG CALL`), — на ней держится `ModU64::assert_zero_mod`
(C2a/C2b, проверка чётности Шамира). Без неё `quo * q == sum` выполнялось бы
для любого `sum`.

Встроенная проверка Noir (`check_for_missing_brillig_constraints`) выдаёт 5
предупреждений `bug: Brillig function call isn't properly covered`:
`U128.nr:241` (`reduce_mod_bounded`) и `U128.nr:277` (`centered_mod_bounded`).
Оба — ложные срабатывания: подсказка возвращает пару `(quotient, remainder)`,
остаток отбрасывается (`let (quotient, _) = …`), и проверка считает
неиспользованный выход «неограниченным». Частное там ограничено битово, а
остаток вычисляется в схеме и зажат в `[0, q)`.

## 2. Латентный дефект: неканонический результат `sub` / `inv_mod`

```noir
pub fn sub(self, lhs: Field, rhs: Field) -> Field {
    let (res_u64, underflow) = unsafe { __sub_with_underflow_u64(lhs, rhs, self.m) };
    if underflow {
        assert(lhs + (self.m as Field) == rhs + (res_u64 as Field), ...);
    } else {
        assert(lhs == rhs + (res_u64 as Field), ...);
    }
    res_u64 as Field
}
```

И флаг `underflow`, и `res_u64` — подсказки. При `lhs >= rhs` годятся обе ветки:
честная (`res = lhs - rhs`) и «заём» (`res = lhs - rhs + m`; это `< 2m < 2^63`,
проверку `u64` проходит). Проверки `res < m` нет. (В `ModU128::sub` то же самое,
но `ModU128` авторы целиком помечают как небезопасный для подсказок — см. поправку.)

`inv_mod` проверяет только `mul_mod(val, result) == 1`; `mul_mod` сам
редуцирует, поэтому проходит `result = inv + k·m` при любом `k`, пока
`result < 2^64`.

Для сравнения: `neg` корректен (`val + res == m` фиксирует `res`), `mul_mod`,
`reduce_mod`, `add` в U64 корректны (остаток зажат `< m`, частное `< 2^64`).
`ModU128::reduce_mod` неоднозначен, но это авторы сами документируют
(комментарий у `reduce_mod_bounded`) и используют его только в `bin/config` на
константах.

### Подтверждение

Сканер, мини-схемы `lat/*.nr` (входы `< m`, как требует документация,
`m = 1000003`), `--targets returns --fixed all-params`:

| мини-схема | вердикт | свидетель |
|---|---|---|
| `sub64` | **unsafe**, Certified (перепроверено на 14 опкодах ACIR) | `lhs = rhs = 0` → `0` и `1000003` |
| `sub128` | **unsafe**, Certified (13 опкодов) | `lhs = rhs = 0` → `0` и `1000003` |
| `inv64` | unknown (контрпример солвера отвергнут ACIR) | — см. PoC ниже |
| `neg64` | verified | — |
| `mul64` | unknown (контрпример солвера отвергнут ACIR) | честно корректен |

`inv64` — пример того, что `unknown` не означает «безопасно»: дефект есть, но
солвер нашёл только ложный (выходящий за `RANGE(64)`) контрпример.

PoC на исполнение (`poc/`): тела `ModU64::sub` и `ModU64::inv_mod` скопированы
дословно, честная подсказка заменена злонамеренной. `nargo execute`:

```
lhs = 5, rhs = 3, val = 3
[poc] Circuit witness successfully solved
[poc] Circuit output: (0x02, 0x0f4245, 0x0a2c2d, 0x196e70)
#   честный sub = 2,      злонамеренный sub = 1000005 = 2 + m
#   честный inv = 666669, злонамеренный inv = 1666672 = 666669 + m
```

### Достижимость

`grep` по `circuits/`: `.sub(`, `.inv_mod(`, `.neg(`, `.div_mod(` вызываются
только в `#[test]` (`polynomial.nr`) — ни одна боевая схема их не использует.
`bin/config` использует только `mul_mod`/`add` на константах. Значит, сейчас
это **латентный** дефект публичного API библиотеки `lib`: первый же вызов `sub`
или `inv_mod` на значении, которое дальше хэшируется в коммитмент или
сравнивается с публичным входом, станет недоограниченностью.

Исправление — та же граница, что уже стоит в `reduce_mod`:
`assert(res_u64 < self.m)` в `ModU64::sub` и `ModU64::inv_mod`. Это одна строка
на функцию. Альтернатива — дописать в doc-комментарий оговорку, как авторы
сделали для `ModU128`.

## 3. C7 `decrypted_shares_aggregation`: ручной разбор

C7 — единственная боевая схема с содержательными подсказками; она доказывает,
что опубликованный открытый текст есть расшифровка долей (CRT + округление BFV).
Для каждой подсказки авторы приводят довод единственности; все проверены вручную
на обоих пресетах:

- `reduce_mod_bounded`: частное `< 2^BIT_K`, остаток в `[0, q)` →
  `q·quot + rem < 2^(BIT_K+BIT_Q+1) ≪ p` (insecure: 2^79, secure: 2^125), значит
  равенство в поле — целочисленное, пара единственна.
- `inv_mod_bounded`: обратный зажат в `[0, q)`, проверка через `reduce_mod_bounded`.
- Garner: `u = r0 + q0·s1 + …`, каждый шаг `< q_l` → `u < Q`, подсказок нет.
- `rounded_decode`: `rounded < 2^BIT_T`, остаток в `[0, Q)` через
  `assert_in_range::<BIT_Q_TOTAL>`; secure: `Q < 2^175`, `t·u + half < 2^196`,
  `Q·2^20 + Q < p` → единственно. `rounded == t` достижимо только при
  `u > Q·(t−½)/t` и корректно сворачивается в 0.
- Лагранж: знак `(−1)^i` для отсортированных id верен; id ≤ 19, произведения
  `< 2^39`, все редукции в границах `BIT_K`.

Вывод разбора: при фиксированных долях и id декодированное сообщение
единственно; дефекта не найдено.

### Сканер на C7

Чтобы спросить именно «определён ли открытый текст долями», а не «единственны ли
подсказки при уже заданном `message`», сделана обвязка (`harness/`):
`execute_decode()` возвращает декодированные коэффициенты вместо сравнения с
публичным `message` (`execute_decode.patch`), `MAX_MSG_NON_ZERO_COEFFS = 2`
(логика по коэффициентам одинакова). Два варианта: `c7_decode` (id — входы,
194 опкода ACIR) и `c7_ids` (id = `[1, 2]` константой, 110 опкодов).

Положительный контроль (защита от пустого результата, см. docs/research/RESEARCH_LOG.md):
`mut_garner.patch` — убрана граница частного в `reduce_mod_bounded`
(остаток становится свободным); `mut_rounded.patch` — в `rounded_decode`
верхняя граница остатка заменена битовой `< 2^72` при `Q ≈ 2^72 − 2^54.3`
(тонкий мутант: неоднозначность только в окне ширины ~2^54).

Результат: **вердикта нет ни для обвязки, ни для мутантов.**

- cvc5 / FF, бюджет `--max-range-bits 16` (по умолчанию): все `RANGE` шире 16
  бит отброшены; солвер раз за разом даёт контрпримеры с огромными значениями,
  ACIR-перепроверка их отвергает, процесс растёт до 5–7 ГБ и убивается OOM
  (cgroup, 15 ГБ на 4 процесса) через 15–25 минут — в том числе на `mut_garner`,
  где неоднозначность очевидна.
- cvc5 / FF, `--max-range-bits 48` (диапазоны 36–42 бит раскладываются точно,
  72-битный отброшен), `c7_ids` + `mut_garner`: таймаут 1200 с, вердикта нет.
- z3 / NIA, `c7_ids` + `mut_garner`, лимит памяти 5 ГБ: таймаут 900 с,
  вердикта нет.

| прогон | обвязка | `mut_garner` | `mut_rounded` |
|---|---|---|---|
| `c7_decode`, cvc5/FF, 16 бит | остановлен на 12 мин | остановлен на 12 мин | остановлен на 12 мин |
| `c7_ids`, cvc5/FF, 16 бит | OOM, 1475 с | OOM, 1072 с | OOM, 905 с |
| `c7_ids`, cvc5/FF, 48 бит | — | таймаут 1200 с | — |
| `c7_ids`, z3/NIA | — | таймаут 900 с | — |
| `--no-solve` (только пропагация) | 22 из 22 целей `unknown` | то же | то же |

Раз даже очевидный мутант не решается, `unknown` на обвязке ничего не говорит о
корректности C7. Вывод о C7 держится только на ручном разборе выше.

Это ровно узкое место, названное в `sota_tools_techniques.md` (Q1, Q5 п. 4):
битовые разложения диапазонов 36–72 бит — главный тормоз FF-солвера.

## 4. Что дальше

1. По желанию — сообщить Interfold о `ModU64::sub`/`ModU64::inv_mod` (PR на
   две строки или issue; это не уязвимость, security-канал не нужен).
2. Для C7 и подобных схем «частное + остаток в окне» нужен не SMT, а лемма:
   шаблон `n == q·quot + rem`, `quot < 2^a`, `rem ∈ [0, q)`,
   `2^a·q + q < p` ⇒ `quot, rem` единственны. Это прямое расширение слоя
   `translate/uniqueness.rs`; после него C7 должен закрываться пропагацией без
   солвера, а мутанты — давать `unsafe`. Это и есть следующая задача для
   адаптера по итогам этой цели.
3. Остальные кандидаты по рейтингу: ZKPassport (`exclusion-check`,
   `facematch`) — нужна сборка на beta.22+ и проверка совместимости формата ACIR.
