их собственный корпус `compile_success_no_bug` закрепляет молчание на несоундной
программе, а цена обхода — одна строка.

## 1. Задача и что было не так в исходном МВП

Цепь называется **недоограниченной**, если существуют два различных набора
значений свидетелей, которые удовлетворяют одной и той же системе ограничений,
совпадают на зафиксированных входах и **расходятся** на целевом значении.
Практический смысл: доказывающий может выдать доказательство для утверждения,
которого честная программа не допускает.

Формально ищется решение задачи самокомпозиции: две копии системы `x*` и `y*`,
общие входы, и требование `x_t ≠ y_t` для целевого свидетеля `t`.

### Причина ложных срабатываний в исходном МВП

Исходный инструмент резал конус влияния по множеству «известных» сигналов, то
есть тех, что уже были выведены распространением. Для таких сигналов в задачу
самокомпозиции выдавалось только равенство `x_s = y_s`, но **само определение**
сигнала в срез не попадало. В результате модель теряла ограничения и объявляла
недоограниченными цепи, которые на деле детерминированы.

**Исправление:** резать разрешено **только** по провабельно константным
проводам, и такие провода закрепляются равенством с константой (`VarEq`), а не
просто равенством между копиями. Сигнал, который «выведен, но не константа»,
режущей границей быть не может.

Проверка исправления: на `examples/verified_division_hint` прежняя версия
выдавала `unsafe`, после исправления — корректный вердикт.

## 2. Метод: три независимых движка

Ключевое решение — **не полагаться на один механизм**. Находка считается
состоятельной, когда её подтверждают механизмы с разными режимами отказа.

### 2.1. Поиск мутацией и починкой (`src/mutate.rs`)

Прямой решатель ACIR. Берёт честный набор свидетелей, меняет один из них и
пытается **починить** остальные так, чтобы все опкоды снова выполнялись.

Устройство починки — два вложенных цикла до неподвижной точки:

* **внутренний** переносит выведенные значения между проходами: ограничение с
  двумя неизвестными пропускается на одном проходе и решается на следующем,
  когда другое ограничение зафиксировало одну из них. Гаджет `IsZero` требует
  именно этого: `flag = 1 - x*inv` имеет две неизвестные, пока `x*flag = 0` не
  зафиксирует флаг, и только затем следует обратный элемент;
* **внешний** перезапускается с нуля, когда пришлось поправить **подсказку**,
  потому что всё выведенное до правки выводилось из неверного значения.

Важное решение: значения прочих подсказок **не копируются** из честного запуска,
а оставляются открытыми. Доказывающий выбирает все свои подсказки вместе.
Копирование было ошибкой, которая скрывала подделку приведения `Field as u128`:
атаке нужно, чтобы обратный элемент гаджета `IsZero` двигался вместе с
проверяемым значением, а при закреплённом честном обратном уравнение гаджета
загоняло флаг в честную ветку и попытка отвергалась на следующем ограничении.

**Перебор в точках неоднозначности.** Если нарушение может поглотить несколько
открытых подсказок сразу, выбор одной из них — настоящая развилка. Раньше поиск
там сдавался, из-за чего был структурно слеп ко всему, что предикатно по `<` и
`>`: любое сравнение целых порождает подсказку деления с **двумя** выходами.
Теперь перебирается до четырёх вариантов выбора. Соундность держит сертификат;
честность в обратную сторону тоже: если перебор был усечён, результат
понижается с «опровергнуто» до «не решено».

### 2.2. Сертификат (`src/certify.rs`)

Независимый вычислитель ACIR, перепроверяющий находку с нуля: совпадение на
входах, расхождение на цели, и затем **все** опкоды. Возвращает
`Certified` / `Refuted` / `Incomplete`, причём `Incomplete` — обязательно, если
проверено ноль опкодов: иначе вырожденная проверка выглядела бы как успешная.

### 2.3. SMT-запрос единственности (`src/solver.rs`)

Путь в духе Picus: задача самокомпозиции передаётся решателю. Работает с
абстракцией и уточнением (CEGAR) по срезам конуса; ослабленный уровень — это
надаппроксимация, поэтому `UNSAT` на нём **доказывает** единственность.

### 2.4. Статический проход (`src/explain.rs`, команда `unpinned`)

Появился последним и оказался самым продуктивным. Не требует ни свидетеля, ни
исполнения — только компиляции. Это принципиально: в кампаниях примерно каждая
седьмая программа честно не исполняется, и там поиск не начинается вовсе; а
целые корпуса Noir вообще не содержат входных файлов.

Проход берёт множество свидетелей, **доказуемо** определённых входами, и ищет
среди остальных подсказки, имеющие форму найденных классов.

Правила определённости, каждое соответствует реальному приёму кодогенерации:

| правило | что распознаёт |
| --- | --- |
| позиционное разложение | `известное - c0*d0 - c1*d1 - ... = 0` с **сверхвозрастающими** весами и ограниченными разрядами. Покрывает и деление на два слагаемых, и восьмиразрядное разложение `u64` |
| чтение из памяти | значение определено, если определён индекс и определены все ячейки блока |
| гаджет `IsZero` | `y*inv + flag - 1 = 0` вместе с `y*flag = 0` определяют обе части, когда `y` известно |
| неявные границы `AND`/`XOR` | эти чёрные ящики ограничивают разрядность входов и выхода — тот же факт, на который опирается пасс Noir `redundant_range` |
| перенос границы через сдвиг | `shifted = value + offset` с границей на одной части даёт границу на другой |

Границы хранятся как большие числа, а не машинные слова: приведение
`Field as u8` делит элемент поля на малую младшую часть и **246-битную**
старшую, и отбрасывание широкой границы оставляло старший разряд без границы —
а в поле старший разряд всегда поглотит изменение младшего, если граница этого
не запрещает.

**Что утверждается, а что нет.** Перечислить опкоды, касающиеся свидетеля, —
точная операция. Решить, фиксирует ли `AssertZero` значение, в общем случае
нельзя. Поэтому вердикт утверждает лишь выводимое из самого списка:

* `BoundedNeverPinned` — свидетеля упоминают только его определение и проверки
  диапазона;
* `OnlyVanishingConstraints` — каждое ограничение умножает свидетеля на другого
  свидетеля, и при его нуле выполняется для любого значения;
* `PropagatesFreedom` — каждое ограничение двигает ещё одного свидетеля из той
  же находки, то есть связывает двоих и не фиксирует ни одного;
* `Asserted` — во всех прочих случаях вердикт остаётся **открытым**.

## 2bis. Как устроен фаззинг: четыре разных конвейера

Слово «фаззинг» здесь покрывает четыре схемы, устроенные по-разному. Их
различает **оракул** — то, что говорит «вот это неправильно». Генератор лишь
поставляет программы; вся сила в оракуле.

### A. Их генератор + наш оракул

`tools/ast_fuzz_campaign.py`, `tools/unpinned_campaign.py`

1. `tooling/ast_fuzzer` самого Noir печатает случайную программу на Noir.
2. Мы её компилируем `nargo`, подбираем входы и исполняем честно — получаем
   свидетеля.
3. **Наш** механизм спрашивает: существует ли *второй* свидетель, совпадающий на
   входах и расходящийся на выходе.

Оракул — единственность свидетеля. Это свойство их собственные фаззеры **не
проверяют**: они сравнивают честное исполнение двух конвейеров, а честное
исполнение совпадает и на недоограниченной схеме. Расходится только
злонамеренное.

### B. Наш генератор + внешний оракул

`tools/stress_gen.py`, `tools/hash_diff.py`, `tools/diff_exec_gen.py`

1. **Мы** строим программы в формах, нагружающих рискованные проходы:
   условная запись в массив, ссылки, цепочки приведений, знаковая арифметика,
   векторы, циклы с предикатом.
2. Ожидаемый ответ вычисляется **независимо, в Python**, по той же семантике.
3. Сравниваются три вещи разом: ответ Noir против ответа Python; ACIR против
   Brillig; и ограничены ли подсказки, которые породил сам компилятор.

Оракул внешний — не компилятор против самого себя, а компилятор против ответа,
полученного другим путём. Сюда же относится сверка `blake2s`, `sha256_compression`,
`keccakf1600` и арифметики кривой с независимыми реализациями.

### C. Наш анализ по их корпусу — без фаззинга вообще

`tools/scan_corpus.sh`, `tools/noir_testsuite_scan.py`

Берутся программы, написанные и закоммиченные командой Noir, компилируются, и по
ним прогоняется наш статический проход. Ничего случайного здесь нет. Именно так
найдена недоограниченная программа в их корпусе `compile_success_no_bug`.

### D. Их фаззер, починенный нами — наш механизм не участвует

`tooling/ssa_fuzzer` + наш `driver.rs`

1. Их фаззер строит **SSA напрямую**, минуя язык, и достаёт до форм, которые
   через исходник не выразить.
2. Одну и ту же программу он компилирует **пятью** способами: два времени
   исполнения (ACIR и Brillig) на нескольких режимах оптимизации — с константными
   аргументами, с идемпотентной морфировкой, без удаления мёртвого кода, без
   упрощений.
3. Он **сам** сравнивает результаты и падает при расхождении.

Наш механизм здесь не используется вовсе: это Noir против Noir. Наш вклад в том,
что четыре из пяти режимов были помечены как неиспользуемые и не включены в их
боевой цели, а два из них к тому же были сломаны. Мы написали драйвер,
запускающий фаззер без libFuzzer, включили все режимы и починили обвязку
(см. раздел 9bis и `findings/ssa-fuzzer-constant-mode-broken/`).

### Почему схем несколько

Каждый оракул слеп к своему. Единственность свидетеля (A) ничего не говорит о
правильности вычисления. Внешний ответ (B) ничего не говорит о недоограниченности.
Сравнение режимов (D) молчит, если оба конвейера ошибаются одинаково. Поэтому
конвейеры не заменяют друг друга, а закрывают разные классы дефектов — и находки
распределились ровно по этому признаку: бреши чекера нашла схема A и C, падение
компилятора — схема D.

## 3. Найденные дефекты

Все шесть воспроизводятся на выпущенной beta.26.

### 3.1. Недоограниченная программа в собственном эталоне Noir

`findings/no-bug-corpus-underconstrained/` — **самая сильная находка**.

`test_programs/compile_success_no_bug/regression_11490` входит в корпус, который
утверждает, что чекер недоограниченности обязан молчать. Он молчит. Программа
при этом несоундна.

```noir
unconstrained fn f(input: u32) -> [u8; 2] { [input as u8; 2] }

fn main(input: u32, expected_sum: pub u32) {
    let data = unsafe { f(input) };
    let mut sum: u32 = 0;
    for i in 0..2 { sum += data[i] as u32; }
    assert(sum == expected_sum);
    assert(sum < 1000000);
}
```

Вся схема — четыре строки:

```
private parameters: [w0]              // input
public parameters: [w1]               // expected_sum
BRILLIG CALL inputs: [w0], outputs: [[w2, w3]]
RANGE w2, 8 bits ; RANGE w3, 8 bits
ASSERT w3 = w1 - w2                   // единственная связь
```

**Вход `w0` не входит ни в одно ограничение.** Честно `f` возвращает
`[input as u8; 2]`, поэтому `expected_sum` обязан равняться `2*(input as u8)`.
Схема этого не требует: ей довольно `w2 + w3 = expected_sum`.

| | |
| --- | --- |
| `nargo execute`, `input = 1, expected_sum = 2` | проходит |
| `nargo execute`, `input = 1, expected_sum = 100` | **`Cannot satisfy constraint`** — программа отвергает |
| схема при `w0=1, w1=100, w2=50, w3=50` | **`no-violation`** — схема принимает |

**Контроли:**

| назначение | результат |
| --- | --- |
| `w2=50, w3=49` (сумма не сходится) | **отвергнуто** на опкоде 5 |
| честная пара `w0=1, w1=2, w2=1, w3=1` | принято |
| `w0=77777`, те же подделанные байты | **принято** — приватный вход ни на что не влияет |

Последняя строка решающая: какой бы `input` доказывающий ни зафиксировал, он
удовлетворит схему для любого `expected_sum` меньше 512, разложив его на два байта.

Комментарии самого теста признают, что первое ограничение «не связывает входы и
выходы вызова `f`», а второе выглядело бы достаточным только из-за исключения
для ограничения против константы (см. 3.2). Тест закрепляет молчание в корпусе,
чьё имя утверждает отсутствие дефекта.

### 3.2. Ограничение, которое ничего не фиксирует

`findings/non-pinning-constraint-silences-checker/`

```noir
unconstrained fn hint(x: Field) -> Field { x }

fn main(a: Field) -> pub Field {
    let h = unsafe { hint(a) };
    assert(h != 0);
    h
}
```

Шесть строк. Компилятор молчит, публичный выход — свободное значение Brillig.
`assert(h != 0)` исключает одно значение из всего поля.

**Причинность — таблица, не зависящая от чтения исходников компилятора:**

| строка | компилятор | `h` определён? |
| --- | --- | --- |
| ассерта нет | `bug: ... isn't properly covered` | нет |
| `assert(h != 0)` | **молчит** | **нет** |
| `assert(h == a)` | молчит | да |

Чекер не отличает вторую строку от третьей.

**Охват класса** (все формы переживают оптимизацию и не определяют подсказку):

| ограничение | компилятор | второй свидетель |
| --- | --- | --- |
| `assert(h != 0)`, `assert(h * h != 7)` — Field | молчит | да |
| `assert(h < 100)`, `assert(h > 2)`, `assert(h >= 3); assert(h <= 9)` — u8 | молчит | да |
| `assert(h & 1 == 0)` — u8 | молчит | да |
| `h.assert_max_bit_size::<8>()` — Field | молчит | да |
| `assert(h == h)` | помечает *(ограничение сворачивается оптимизатором)* | да |
| `assert(h[0] != 0)` на `[Field; 4]`, наружу `h[0]` | помечает *(жив поэлементный учёт)* | да |

Класс **выживает при обычном использовании** подсказки: в арифметике
(`h * 3 + 1`), как индекс массива, и в виде ограниченного по разрядности остатка.
Последняя форма практически значима: ограничить подсказку по разрядности и
положиться на чекер в остальном — это ровно то, как пишут гаджет деления.

**Усиление: одного слабого ограничения хватает на цепочку.** В
`arguments_intersect` написано: *«если испорченный вход уже был ограничен, его
можно использовать»*. Подсказка, зачтённая как ограниченная, дальше используется
для очистки следующей, и слабость передаётся по цепи:

| программа | компилятор |
| --- | --- |
| цепочка из трёх подсказок **без** `assert(h1 != 0)` | помечает |
| та же цепочка с одним `assert(h1 != 0)` | **молчит** |

Цена класса не растёт с числом слабых мест: достаточно одного, чтобы ослепить
чекер на всё остальное.

**Происхождение.** В док-комментарии `try_constrain` перечислены исключения из
правила, и одно из них — «*если ограниченное значение одно (выход против
константы)*», реализованное как `let is_against_const = constrained_values.len() == 1;`.
В скобках заложено допущение, что сравнение выхода с константой его фиксирует.
`assert(h != 0)` и `assert(h < 100)` — сравнения с константой, которые не
фиксируют ничего. Модель чекера видна и в его собственных тестах: там стоит
комментарий `constrain v18 == u1 1    // This constrains v8`, то есть фиксация
булева результата сравнения считается фиксацией операнда.

### 3.3. Ограничение под предикатом

`findings/predicated-constraint-silences-checker/`

```noir
fn main(a: Field, c: bool) -> pub Field {
    let h = unsafe { hint(a) };
    if c { assert(h == a); }
    h
}
```

Исходник читается как полностью корректный: подсказка **и правда** ограничена
равенством `a`. Но ограничение предикатно по `c`, а `c` выбирает доказывающий.

**Соундность зависит от значения входа:**

| `c` | честный выход | второй свидетель | поиск |
| --- | --- | --- | --- |
| `0` | 5 | **есть, выход 6** | 3 находки за 5 попыток |
| `1` | 5 | нет | 0 находок за 24 попытки |

Одна и та же схема, меняется только вход. ACIR: `ASSERT 0 = -w0*w1 + w1*w3`,
то есть `c*(h - a) = 0`. Коэффициент при подсказке — сам `c`.

**Охват:**

| форма | компилятор | второй свидетель |
| --- | --- | --- |
| `if c { assert(h == a) }`, `c` — вход | молчит | да |
| `if a > 10 { assert(h == a) }` | молчит | да |
| `if c { if d { assert(h == a) } }` | молчит | да |
| `if g { ... }`, где `g` — сама подсказка | **помечает** | да |
| `if c { ... } else { assert(h == 0) }` | молчит | нет |

Две последние строки ведут себя правильно и обе поучительны: предикат-подсказку
чекер покрывает, а `if` с полным `else` ограничивает подсказку на каждом пути,
и молчание там верно. Опасна середина таблицы — обычное условие над обычными
данными.

### 3.4. Порог длины массива

`findings/array-output-length-threshold/`

```noir
unconstrained fn hint(x: Field) -> [Field; 65] { [x; 65] }

fn main(a: Field) -> pub Field {
    let h = unsafe { hint(a) };
    assert(h[0] == a);   // ограничен только элемент 0
    h[1]                 // отдаётся наружу и свободен
}
```

| длина массива | компилятор |
| ---: | --- |
| 4, 64 | помечает |
| **65, 128** | **молчит** |

64 — это `DEFAULT_MAX_ARRAY_OUTPUT_LENGTH`, и компромисс задокументирован в
исходниках: «массивы длиннее считаются ограниченными, если ограничен хоть один
элемент».

**Причинность доказана, а не выведена из совпадения порога.** Лимит настраивается
скрытым флагом драйвера, поэтому одна и та же программа с 65 элементами:

| лимит | результат |
| ---: | --- |
| 64 (по умолчанию) | молчит |
| 65, 128 | **помечает** |

Чекер эту программу видит; подавляет её ровно сравнение `length.0 <= max_array_output_length`.

### 3.5. Ложное срабатывание по расстоянию предков

`findings/ancestor-distance-false-positive/`

Зеркальный случай: `bug:` на **корректной** программе. `t` и `r` строятся
одинаковыми цепочками из `h` и `a`, поэтому `assert(t == r)` эквивалентно
`h == a`, и подсказка определена при любой длине цепочки.

| длина цепочки | инструкций | компилятор |
| ---: | ---: | --- |
| 0…5 | до 10 | молчит |
| 6…24 | 12 и более | **помечает** |

Порог — `DEFAULT_MAX_ANCESTOR_DISTANCE = 10`. Причинность доказана тем же
приёмом: на программе с цепочкой 6 лимит 10 даёт `bug:`, лимиты 14/20/40 —
молчание. Поведение одинаково на выпуске и на nightly, регрессии нет.

### 3.6. Кандидат из фаззера, объяснённый классом 3.2

`findings/nightly-returndata-loop/` — программа на 5129 символов, найденная
кампанией. Долго не поддавалась сокращению; причина выделена **из ACIR**, а не
из исходника:

```
761: BRILLIG CALL predicate: -w419 + 1, ... outputs: [w485]
762: BLACKBOX::RANGE input: w485, bits: 8
763: ASSERT w485 = -w419*w483 + w419*w485 + w2
764: INIT RETURNDATA b0 = [w2]
```

`w485` встречается ровно в трёх опкодах, публичный выход `w2` — ровно в двух.
На честном запуске `w419 = 0`, и строка 763 вырождается в `w485 = w2`. Значит
пара ограничена **только** 8-битной проверкой диапазона. Это в точности класс
3.2, добытый фаззером, а не руками.

## 4. Как проверялась каждая находка

Единый стандарт, применённый ко всем:

1. **Компиляция строго**: проверяется код возврата, а не только отсутствие
   диагностики. Отдельная ошибка ранней итерации: вспомогательный скрипт
   сообщал «молчит», когда компиляция на самом деле **падала**.
2. **Всегда `--force`**: без него `nargo compile` берёт кэш, и диагностика не
   печатается повторно. Один ранний вывод пришлось отозвать именно из-за этого.
3. **Честный запуск** и **подделка** при тех же входах.
4. **Независимая перепроверка** другим движком: `feasible --propagate-only`
   (распространение констант) вместо обхода опкодов в сертификате.
5. **Контроль**: тот же свидетель с выходом, возвращённым к честному значению,
   обязан быть **отвергнут**. Без этого нельзя отличить настоящую проверку от
   вырожденной, проходящей всегда.
6. **Проверка на выпуске**, а не только на nightly.
7. **Исключение задокументированных причин**: пересборка с обоими эвристическими
   лимитами, поднятыми до 4096 и 500. Если диагностика не появляется, находка не
   объясняется ни одним из известных компромиссов.

### 5.1. Против собственной разметки Noir

| --- | --- |

### 5.4. Кампании

| кампания | объём | итог |
| --- | ---: | --- |
| генератор Noir (`ast_fuzzer`) + оракул единственности | 400 + 400 | находок 0 |

оптимизатор несоундности не вносит.

## 5bis. Целенаправленный поиск дефекта кодогенерации

Раздел отвечает на вопрос, отдельный от разделов 3–5: есть ли в Noir **ошибка
кодогенерации**, то есть случай, когда компилятор порождает схему, вычисляющую
не то, или принимающую то, что программа отвергает. Это не то же самое, что
брешь в чекере: чекер обязан предупреждать, а кодогенерация обязана быть верной.

### Оракулы

Использованы четыре независимых вида проверки:

1. **Внешний ответ.** Прицельный генератор строит программы в формах, нагружающих
   рискованные проходы, и вычисляет ожидаемое значение **в Python** по той же
   семантике. Сравнивается не компилятор с самим собой, а компилятор с ответом,
   полученным независимо.
2. **Две настройки одного конвейера.** Один исходник исполняется на трёх уровнях
   `--inliner-aggressiveness` и на разных версиях компилятора.
3. **Два конвейера.** Тот же исходник переписывается в `unconstrained fn main`,
   что переводит его на конвейер Brillig вместо ACIR.
4. **Программа обязана отказать.** Часть случаев строится с заведомым
   переполнением или чтением за концом массива; приём числа вместо отказа
   означает дефект.

Плюс сверка криптографических примитивов с реализациями, не разделяющими с Noir
ни строки кода.

### Результат

| направление | объём | расхождений |
| --- | ---: | ---: |
| уровни инлайнера, сгенерированные программы | 362 | 0 |
| версии компилятора | 290 | 0 |
| прицельный генератор против внешнего оракула | 700+ | 0 |
| `blake2s` против `hashlib` | 300 | 0 |
| `sha256_compression` против своей реализации раунда | 200 | 0 |
| `keccakf1600` против своей реализации перестановки | 120 | 0 |
| `embedded_curve_add` против арифметики Grumpkin | 39 | 0 |
| `multi_scalar_mul` против той же арифметики | 21 | 0 |
| корпус `execution_failure` (обязаны отказать) | 71 | 0 |
| собственные тесты Noir по уровням оптимизации | 39 | 0 |
| дифференциальное исполнение по корпусу Noir | 182 | 0 |

**Каждый криптографический оракул калибровался** на известном значении до
запуска веера. На `sha256_compression` это оказалось необходимо: Noir возвращает
результат с прямой подачей Дэвиса–Мейера, и без калибровки «не совпали» бы все
200 входов, то есть был бы объявлен несуществующий дефект.

Веера намеренно смещены в краевые случаи: длины вокруг границы блока в 64 байта
для хеша; `0`, `2^n - 1`, `2^(n-1)` для целых; удвоение, `P + (-P)`,
бесконечность и скаляр, равный порядку группы, для кривой.

### Вывод

При описанном объёме проверок дефекта кодогенерации не найдено. Прочитаны и
проверены точечными программами шесть проходов оптимизатора; четыре гипотезы о
дефекте выдвинуты и опровергнуты (раздел 7). Чекер недоограниченности Noir
проходится существенно легче, чем его кодогенерация.

**Непроверенным осталось:** рекурсия и `std::verify_proof`, дефункционализация
замыканий, перечисления с `match`, `comptime`-вычисления, а также проходы
`unrolling`, `mem2reg`, `load_store_forwarding` и `alias_analysis`.

## 5ter. Кампания на SSA-фаззере Noir

Отдельная схема (конвейер D раздела 2bis), потребовавшая наибольших вложений и
давшая наиболее поучительный результат.

### Замысел

`tooling/ssa_fuzzer` строит SSA напрямую, минуя язык, и сравнивает одну программу,
скомпилированную несколькими способами. Из **пяти** режимов сравнения четыре
помечены `#[allow(dead_code)]` и не включены в боевой цели, хотя написаны прямо
под дефекты оптимизатора. То есть непрерывная интеграция Noir туда не смотрит, и
это незанятое поле.

`cargo-fuzz` и nightly не требуются: `fuzz_target` сам сравнивает выходы и падает
при расхождении, поэтому достаточно обычного бинарника, перехватывающего панику.

### Что пришлось починить, чтобы схема заработала

| дефект | следствие | чей |
| --- | --- | --- |
| `Constant` сравнивал результат с оставшимся входом | 40 ложных расхождений из 120 | их |
| падение на нечисловом параметре `main` | раунд терялся целиком, программу не проверял ни один режим | их |
| столкновение двух правок: программе с параметрами доставалась пустая карта свидетелей | 10 ложных «Constant failed» подряд | **мой** |
| `NonConstantWithoutDIE` нарушает документированный предпорядок проходов | все 24 события прогона — один и тот же сбой | их, по построению |

Отдельно — производительность. Драйвер мутировал одну программу по кругу, и она
росла к пределам: 216 программ в минуту вначале, 65 к восемнадцатой. Замена на
популяцию из восьми родословных с перезапуском дала **~9300 в минуту**, примерно
в сто сорок раз.

### Результат: 1 363 800 программ

* **68 событий**, из них 64 неудачи компиляции и **4 расхождения значений**;
* единственный вид внутренней ошибки компилятора за весь прогон — уже найденная
  паника `ToRadix` (197 срабатываний), что подтверждает её достижимость из многих
  форм SSA, а не только из нашего примера;
* расхождений значений между режимами, достижимых из настоящего исходника, —
  **ноль**.

### Разобранное расхождение: знаковое приведение

Все четыре расхождения — одна закономерность: то же знаковое число иной
разрядности (`-9` в 16 битах против 8, `-113` в 64 против 8 и так далее).
Повтор с печатью SSA:

```
NonConstant:  b0(..., v3: i8, ...):  v6 = cast v3 as i16 ;  return v6   -> 247
Constant:     b0():                  return i16 -9                      -> 65527
```

Константный путь расширяет знак, обычный — нет. Два пути компилятора расходятся
в семантике одной инструкции.

**Но из настоящего исходника это недостижимо:**
`fn main(x: i8) -> pub i16 { x as i16 }` при `x = -9` даёт `-9` в обеих средах
исполнения. Фронтенд порождает для знакового приведения составную машинерию, а
голый `cast i8 as i16` строит только фаззер. Записано как внутренняя
несогласованность, а не как опасный дефект.

### Во что упирается схема

* **Нет внешнего эталона.** Сравниваются режимы между собой; если оба ошибаются
  одинаково, схема молчит. Этот пробел закрывает конвейер B.
* **SSA, которого фронтенд не порождает.** Постоянный поток находок, законных на
  уровне SSA и недостижимых из кода; отделять их приходится вручную, воспроизводя
  случай на настоящем исходнике.
* **Неподдерживаемые режимы.** Три дефекта обвязки на пять режимов — всё, что
  помечено `dead_code`, работает не полностью.

## 6. Отрицательные результаты с доказанным охватом

Важно для работы: это не «инструмент промолчал», а измеренная глубина поиска.

* **Каноничность битового разложения чиста.** `to_le_bits::<254>` — 8414 попыток
  поиска, 0 находок; `to_le_bits::<64>` — 1150; `to_le_bytes::<32>` — 2377.
  Защита в `noir_stdlib/src/field/mod.nr` сравнивает разложение со старшими
  битами модуля и требует `assert(ok)`. При `N < 254` проверка пропускается, но
  это безопасно, так как `2^N - 1 < p`.
* **Структурных обходов чекера не нашлось.** Вложенные массивы `[[Field; 2]; 4]`,
  кортежи, динамический индекс `assert(h[i] == a)`, ограничение внутри
  `#[fold]`-функции — всё помечается. Векторы из unconstrained **запрещены
  языком**: «Vectors cannot be returned from an unconstrained runtime to a
  constrained runtime». Значит обходы — ровно две задокументированные константы,
  а не структурные дыры.
* **Второе исключение из списка не эксплуатируется.** «Нет входных аргументов»:
  и при отсутствии аргументов, и при константных аргументах подсказка
  сворачивается в константу. Доказательство, а не догадка: `scan` даёт
  `1 target — 1 verified`.
* **Второй чекер мины не содержит.** `check_for_underconstrained_values.rs` —
  это union-find связность, по устройству ловит только полностью несвязанные
  вызовы Brillig.

## 7. Опровергнутые гипотезы

Раздел важен: он показывает, где Noir оказался прав, и какие ошибки допускал я.

### 7.1. Оптимизатор диапазонов ACIR под ложным предикатом

Гипотеза: `redundant_range.rs` снимает явную проверку диапазона, полагаясь на
индексацию массива, а под ложным предикатом это рассуждение рушится.
**Опровергнуто:** у `Opcode::MemoryOp` в текущем ACIR нет поля предиката, а
`--print-acir` показывает сохранение `RANGE w0, bits: 32` во всех трёх вариантах
(без индексации, с индексацией, с индексацией под условием). Условная индексация
компилируется в разложение с однозначным решением.

### 7.2. Деление `x / 7` на `u8`

Выглядело как дыра: остаток ограничен тремя битами (0..7), делитель 7, значит
при `x = 7` подошли бы и `(q=1, r=0)`, и `(q=0, r=7)`. **Опровергнуто чтением
всего ACIR:** там есть `ASSERT w4 = w3 + 1` с трёхбитной границей уже на `w4`,
откуда `w3 <= 6`. Поиск подтверждает: 0 находок за 31 попытку.

### 7.3. Приведение `Field as u8`

Гипотеза: старший разряд в 246 бит допускает неканоническое разложение, так как
`256 * 2^246 = 2^254 > p`. Был построен конкретный контрпример
`x = (256*(2^246 - 1) + 5) mod p`. **Опровергнуто чтением всего ACIR:**

```
ASSERT w4 = K - w2 ;  RANGE w4, 246 bits ;  где K = floor(p/256)
BRILLIG CALL -> w5 (обратный элемент к K - w2)
ASSERT w6 = w2*w5 - K*w5 + 1        // флаг «w2 == K»
ASSERT 0 = -w2*w6 + K*w6
ASSERT 0 = w3*w6                    // при w2 == K младшая часть обязана быть нулём
```

Проверено численно: `K` действительно равно `⌊p/256⌋`, а `p mod 256 = 1`,
поэтому одной границы **не хватает** (`256*K + 255 = p + 254`) — и гаджет
`IsZero` нужен ровно для граничного случая. Максимум ровно `p - 1`. Приведение
каноническое, аргумент тонкий.

### 7.4. `checked_to_unchecked` и знаковое расширение

Проход снимает проверку переполнения, опираясь на оценку `required_bit_size`,
которая для приведения берёт **минимум** разрядностей: `min(32, 8)` для
`i8 as u32`. Если бы приведение расширяло знак, значение занимало бы 32 бита при
оценке в 8, и умножение осталось бы непроверенным.

Знаковое расширение подтверждено измерением: `(-1i8) as u32 = 4294967295`. Но
проверка на месте — `a * a` при `x = -1` падает, при `x = 3` даёт 9. Значит в SSA
такое приведение представлено не одним `Cast`, а составной операцией, и оценка не
занижается.

### 7.5. Вынос из цикла операции, способной упасть

Деление на ноль, выход за границы массива и вычитание с недополнением, помещённые
в цикл под ложным условием, — все четыре программы возвращают 0, а не падают.
Предикация обрабатывается корректно.

### 7.6. Снятие проверки диапазона с индекса массива

`redundant_range.rs` действительно **удаляет** 32-битную проверку с индекса: в
ACIR программы `array[index]` нет ни одного `RANGE` на входном параметре. Пасс
полагается на то, что чтение из памяти ограничит индекс сильнее.

Проверено место, где рассуждение могло рухнуть, — **предикатное** чтение
(`if c { v = array[index] }`, а `index` отдаётся наружу). Там проверка диапазона
**сохраняется**: пасс учитывает побочные эффекты.

### 7.7. Снятие проверки диапазона с операндов `AND`/`XOR`

Здесь проверки удаляются полностью: ACIR программы `x & y` — это ровно два
опкода, и ни одного `RANGE` на `x` и `y`, хотя оба объявлены `u8`. Выглядело как
обязанность, делегированная бэкенду и потому не выраженная в ACIR.

**Опровергнуто чтением ACVM:** `acvm/src/pwg/blackbox/logic.rs` вызывает
`check_bit_size` на **обоих** операндах до вычисления результата. Обязанность
разрядности входит в семантику самого ACIR, и удаление явного `RANGE` корректно.

**Общая ошибка в первых трёх случаях одна:** я смотрел часть опкодов вместо всех.
Отсюда рабочее правило: разбирая свидетеля, брать **полный** список опкодов,
которые его упоминают. Оно же положено в основу команды `mutate --explain`.

## 8bis. Целостность проверки: два дефекта в собственном инструменте

Оба найдены во время охоты за багом оптимизатора, и оба били по тому самому
движку, которым перепроверяются находки. Поэтому после каждого исправления все
находки прогонялись заново.

### Вырожденный вердикт

При проверке деления на ноль `feasible --propagate-only` напечатал
`no-violation`, хотя схема этот вход отвергает: в ACIR стоит `b * b_inv = 1`, что
невыполнимо при `b = 0`. Проход **не смог вычислить** это ограничение, поскольку
обратный элемент неизвестен, и промолчал как об успехе. Это едва не стало ложной
находкой.

Добавлен подсчёт охвата: `no-violation (N constraint(s) evaluated)` печатается
только когда вычислены **все** ограничения, иначе `undecided: N of M`. На делении
вердикт стал `undecided: 2 of 9`.

### Непроверяемые чёрные ящики

Тот же движок вообще не проверял `AND`/`XOR` и не считал их в охвате. На программе
`x ^ y` он принимал `x = 300` — значение, которое ACVM отвергает, — и при этом
рапортовал, что вычислил все ограничения.

Исправлено: добавлена проверка обязанности разрядности обоих операндов и
функционального соответствия выхода; неподдерживаемые чёрные ящики и операции с
памятью теперь **увеличивают знаменатель** охвата, чтобы схема из непроверенных
опкодов не могла отчитаться как чистая. Теперь `x = 300` отвергается с
`opcode 0: XOR operand 300 exceeds 8 bits`.

### Перепроверка находок после исправлений

| находка | охват |
| --- | --- |
| не фиксирующее ограничение | `no-violation (2 из 2)` |
| предикатное ограничение | `no-violation (3 из 3)` |
| усиление по цепочке | `no-violation (4 из 4)` |
| массив длиной 65 | `no-violation (2 из 2)` |
| случай с ветвлением | `no-violation (10 из 10)` |
| `regression_11490` | `no-violation (8 из 8)` |

Ни одна не была вырожденной, все шесть в силе.

**Правило, выведенное из обоих дефектов.** Вердикт «нарушений нет» обязан
сопровождаться охватом, а знаменатель охвата обязан включать **все** опкоды, а не
только те, которые движок умеет проверять. Иначе движок, который многого не
умеет, выглядит как движок, всё подтвердивший.

## 9. Границы применимости

Называются прямо, а не замалчиваются.

* **Приведения типов остаются кандидатами.** Проход не воспроизводит граничное
  рассуждение из 7.3, поэтому всякое `Field as uN` попадает в отчёт. Это 38 из
  44 «молчаливых» срабатываний при полном сканировании. Правильное исправление —
  распознавать связку «граница `K - w2` плюс `IsZero` на ней».
* **Деление на не-степень двойки с косвенной границей.** `regression_8236`
  остаётся ложным: там деление на 3, а граница остатка задана через
  промежуточное ограничение (`w7 = w6 + 1` в двух битах).
* **Статический проход — триаж, а не доказательство.** Два ограничения могут
  фиксировать пару **совместно**, чего поэлементное правило не видит.
  Подтверждение кандидата — это `mutate` или `scan` на нём.
* **Криптографические чёрные ящики** (хеши, операции на кривых) моделируются как
  детерминированные функции. Это слепая зона по построению, а не утверждение об
  их корректности.
* **`refuted` — эвристика.** Перебор в точках неоднозначности ограничен четырьмя
  вариантами; при усечении результат честно понижается до «не решено».

## 11. Дифференциальная соундность между уровнями оптимизации

### 11.1 Почему прежний дифференциальный метод не мог найти такой класс ошибок

В разделе 5 описан дифференциальный ЗАПУСК: одна программа собирается при разных
настройках компилятора, затем выполняется на одинаковых входах, и результаты
сравниваются. Метод дал ноль расхождений.

Ноль здесь надо читать правильно. Дифференциальный запуск **принципиально не
способен** обнаружить самый опасный вид ошибки оптимизатора — потерю ограничения.
Рассуждение простое. Пусть оптимизация сочла проверку избыточной и выбросила её.
Честный свидетель эту проверку удовлетворял, поэтому после её удаления он
по-прежнему проходит, и выход не меняется. Оба варианта сборки выдают один и тот
же ответ на любом честном входе. Расхождения не возникает — а схема при этом
стала небезопасной.

Разница между сборками проявляется не в результате на честном входе, а в
**множестве допустимых свидетелей**: у ослабленной схемы оно шире. Значит и
сравнивать надо множества, а не результаты.

### 11.2 Устройство проверки (`tools/diff_soundness.py`)

Для каждой программы:

1. сборка при пяти значениях `--inliner-aggressiveness` — от минимального
   (встраивание практически отключено) до максимального (по умолчанию);
2. `Prover.toml` строится **один раз** по ABI с фиксированным зерном, чтобы все
   уровни получили один и тот же честный вход, иначе вердикты несопоставимы;
3. на каждой сборке — статический проход `unpinned` и поиск второго свидетеля
   `mutate`;
4. расхождение вердиктов между уровнями = кандидат на ошибку компилятора.

**Ограничение, которое пришлось обойти.** Номера сигналов между сборками не
совпадают: инлайнер меняет структуру ACIR, и witness №42 в одной сборке и в
другой — разные величины. Поэтому сравниваются только характеристики, выразимые
через интерфейс программы и не зависящие от нумерации: число незакреплённых
выходов подсказок, число подсказок в воронке и факт нахождения второго
свидетеля.

### 11.3 Почему выбран режим `pure`

Генератор `noir_gen.py` в режиме `pure` выдаёт программы без единой подсказки:
никаких `unsafe`, unconstrained-функций и внешних вызовов. Такая программа
обозначает всюду определённую функцию своих параметров, поэтому ACIR обязан
определять каждый сигнал, как только параметры зафиксированы.

Отсюда порог строже обычного: **любая** находка на **любом** уровне оптимизации —
ошибка компилятора, а не свойство схемы. Оракул не нуждается во внешней
эталонной реализации. Для режима `hints` находка была бы лишь кандидатом, потому
что сгенерированная подсказка может быть недоопределена по существу.

### 11.4 Положение метода среди четырёх конвейеров раздела 2bis

Это пятый конвейер, и он отличается от всех прежних тем, что **сравнивает наш
механизм сам с собой** на выходах компилятора при разных настройках. Эталон здесь
не внешняя реализация и не второй компилятор, а требование внутренней
согласованности: оптимизация обязана сохранять множество допустимых свидетелей.
Такое требование проверяемо без какого-либо эталона вообще, что и делает метод
пригодным для поиска ошибок в самом компиляторе.

### 11.5 Улучшение механизма, вызванное этим конвейером

Первая кампания пятого конвейера дала не только вердикт, но и повод исправить
сам механизм.

**Наблюдение.** В воронке поиска строка «не решено» составляла четверть всех
попыток. Эта доля важна: она в точности отмеряет ту часть пространства, о которой
отрицательный результат ничего не утверждает. Пока она велика, любой наш ноль
слабее, чем кажется.

**Диагностика.** Ввели разбор причин с приведением к виду (номера сигналов и
опкодов схлопываются, чтобы одна проблема не рассыпалась на сотню записей).
Результат оказался однозначным: **все** нерешённые попытки имели одну причину —
исчерпание перебора вариантов, и ни одна не была вызвана немоделируемым опкодом.
Значит покрытие вычислителя ACIR достаточно, а предел лежит в глубине поиска.

**Ложное объяснение и как оно опровергнуто.** Напрашивался вывод: мал бюджет
перебора. Подняли его с 4 до 64 — число нерешённых не изменилось ни на единицу.
Это опровергло объяснение и заставило читать код.

**Настоящая причина.** В точке, где несколько открытых подсказок могут поглотить
невязку, вариант выбирался как `many[preference % many.len()]`. Один и тот же
номер подставлялся во все точки выбора одновременно, то есть перебор шёл по
диагонали декартова произведения. При двух точках по два варианта посещались два
сочетания из четырёх, и увеличение бюджета не добавляло ни одного нового —
диагональ зацикливалась. Вдобавок признак усечения выставлялся при любой
неоднозначности, поэтому отказ всегда понижался с «опровергнуто» до «не решено»,
даже когда пространство выбора было пройдено целиком.

**Исправление.** Номер попытки раскладывается по разрядам смешанной системы
счисления, где основание каждого разряда — мощность соответствующей точки
выбора. Перебор проходит произведение целиком. Признак усечения стал честным:
он поднимается, только если произведение действительно шире бюджета, а цикл
завершается досрочно при исчерпании пространства — и тогда отказ является
настоящим опровержением.

**Измеренный эффект** (одна и та же схема, `attempts=4`):

| настройка        | опровергнуто | не решено |
|------------------|--------------|-----------|
| до исправления   | 392          | 134       |
| после, бюджет 4  | 475          | 51        |
| после, бюджет 16 | 505          | 21        |
| после, бюджет 64 | 509          | 17        |

Одно только исправление при неизменном бюджете сократило долю нерешённых на 62%.
Регрессия проверена: 60 модульных тестов, ни одного отказа.

**Следствие для ранее полученных отрицательных результатов.** Все прежние нули —
1 363 800 программ SSA-фаззера, 205 000 через конвейер единственности, аудит
шести операций боевых библиотек — вынесены механизмом, который в точках
неоднозначности осматривал лишь диагональ пространства выбора. Это не отменяет их,
но требует оговорки, и последующие кампании ведутся на исправленной версии.

**Методическое замечание.** Гистограмма причин указала верное место (перебор
вариантов) и неверную причину (нехватка бюджета). Различить их удалось
единственным способом: применить очевидное лечение и увидеть, что оно не
действует. Диагностика, называющая место, полезна даже тогда, когда её
объяснение ошибочно.

## 12. Два непересекающихся класса ошибок соундности

### 12.1 Как граница метода обнаружилась

В наборе Noir есть каталог `execution_failure`: 75 программ, которые обязаны
падать при выполнении. Это готовый оракул, эталоном служит собственное ожидание
разработчиков компилятора. Прогон всех 75 дал: **упали 71, прошли 3**.

Три программы, проходящие вопреки ожиданию:

1. `regression_claude_1640` — проход `LICM` применил границы индукции цикла
   `while` к соседнему циклу `for` и свернул условие `i < 3` в истину. Из-за
   этого выполняется заведомо ложное утверждение.
2. `regression_claude_1654` — при генерации ACIR безопасное индексное чтение на
   выбранной ветви разрешалось как отключённый доступ, и результат привязывался
   к константе. Формулировка комментария в самом тесте: «доказывающий мог
   удовлетворить схему, которую исходный текст отвергает».
3. `zero_length_array_set_out_of_bounds` — проверка выхода за границы не
   учитывала уплощённый размер при нулевой ширине элемента.

**Проверка на новизну обязательна и здесь она отрицательна.** Все три исправлены
в августе 2026 (PR #13481, #13486, #13462), а использованный `nargo`
1.0.0-beta.26 старше этих исправлений. Новыми находками они не являются.

Ценность в другом: получены три ошибки соундности с известным ответом, то есть
эталон для оценки чувствительности механизма.

### 12.2 Измерение: механизм единственности их не видит

| программа                           | чекер Noir | наш `unpinned` | наш `mutate`  |
|-------------------------------------|-----------|----------------|----------------|
| regression_claude_1640              | помечает  | 0 кандидатов   | 0 находок (7 опровергнуто)  |
| regression_claude_1654              | молчит    | 0 кандидатов   | 0 находок (31 опровергнуто) |
| zero_length_array_set_out_of_bounds | молчит    | 0 кандидатов   | 0 находок (14 опровергнуто) |

Механизм не ловит ни одну — и это **не дефект реализации, а граница метода**.

### 12.3 Почему граница принципиальна

Оракул самокомпозиции спрашивает: существуют ли ДВА свидетеля, совпадающие на
всех зафиксированных входах и различающиеся на целевом сигнале. Это определение
недоограниченности.

У всех трёх ошибок свидетель ЕДИНСТВЕНЕН. Схема детерминирована; она просто
вычисляет не то, что написано в исходном тексте, и принимает витнесс, который
исходник отвергает. Это **неверная компиляция**, и вопрос о числе свидетелей к
ней неприменим.

Отсюда вывод, существенный для постановки задачи:

> Недоограниченность и неверная компиляция — два непересекающихся класса ошибок
> соундности. Один оракул их не покрывает. Для первого нужен механизм
> самокомпозиции; для второго — оракул, сравнивающий поведение схемы со
> СМЫСЛОМ ИСХОДНОГО ТЕКСТА.

Все три ошибки, найденные командой Noir за две недели, относятся ко второму
классу.

### 12.4 Шестой конвейер: оракул неверной компиляции

`tools/mustfail_fuzz.py`. Смысл исходного текста пересчитывается независимо на
Python, проверяются оба направления: где ожидается принятие — схема обязана
принять и выдать то же значение; где ожидается отказ — обязана отказать.
Принятая программа, которую исходник отвергает, и есть неверная компиляция.

Формы порождаются те, в которых жили все три реальные ошибки: цикл `while` и
следующий за ним `for` с условием на той же переменной индукции; предицированное
чтение массива на выбранной ветви; запись по динамическому индексу; вложенные
циклы.

**Чувствительность проверена до кампании, на настоящей ошибке.** Сначала измерена
область срабатывания #13481:

| форма                      | истина | схема |
|----------------------------|--------|-------|
| while i<3, for 0..2, (i<3) | 0      | 20    |
| while i<1, for 0..3, (i<1) | 0      | 0     |
| while i<2, for 0..2, (i<2) | 0      | 20    |
| while i<4, for 0..1, (i<4) | 0      | 10    |

Ошибка проявляется при границе `while` не меньше двух. Затем генератор
воспроизвёл её самостоятельно в форме, которой не было в исходном тесте
(вложенные циклы): схема выдала 12 при истине 10.

Это отличает шестой конвейер от предыдущих пяти: его чувствительность
подтверждена не рассуждением, а срабатыванием на ошибке компилятора с известным
ответом.

### 12.5 Ограничение и способ его снять

Использованный `nargo` старше трёх исправлений, поэтому почти любая находка
шестого конвейера будет повторением уже исправленного. Чтобы искать новое, нужен
компилятор, собранный из свежих исходников: тогда все три исправления уже
внутри, и оракул бьёт по неисследованному.

## 13. Точность на собственном наборе тестов Noir

### 13.1 Постановка

`test_programs/execution_success` — 532 программы, которые команда Noir написала,
поддерживает и считает корректными, с уже зафиксированными входами. Это самая
строгая аудитория для оценки ЛОЖНЫХ СРАБАТЫВАНИЙ: любая пометка здесь означает
либо дефект в коде, который кто-то считал верным, либо ошибку инструмента.

Из корпуса исключены эталонные тесты (`bench_*`): на схемах в сотни тысяч
ограничений поиск не завершается, и без исключения они останавливали весь обход.
Исключение отражено в счётчике, а не скрыто.

### 13.2 Первый прогон и найденная ошибка ИНСТРУМЕНТА

    466 пакетов: находок 1, чистых 442, помечено самим компилятором 6, пропущено 17

Единственная пометка — `fold_out_of_order_calls`: две функции с `#[fold]`,
вызванные в обратном порядке объявления. Программа тривиально корректна,
подсказок в ней нет вовсе.

Причина оказалась в нашем инструменте. Схемы сопоставлялись со свидетелями по
порядку: `functions.iter().zip(&witnesses)`. Но порядок схем — это порядок
ОБЪЯВЛЕНИЯ, а порядок в стеке свидетелей — порядок ВЫЗОВА. Подсхеме `fold_one`
достался свидетель от `fold_two`, и закреплённый сигнал проверялся против чужих
значений.

Отдельно стоит отметить происхождение теста: он написан командой Noir против
ТАКОЙ ЖЕ ошибки сопоставления в их собственном компиляторе — каждая fold-схема
должна получить свою сигнатуру независимо от порядка первого упоминания. Тест
поймал ту же ошибку у нас.

**Исправление.** `pick_matching_witness()`: свидетель подбирается ПРОВЕРКОЙ, а не
позицией — берётся тот из стека, который действительно удовлетворяет схеме, что
решает тот же вычислитель ACIR, который выносит вердикты о находках. Если не
подходит ни один, схема пропускается со счётчиком, а не берётся чужой свидетель
молча.

### 13.3 Повторный прогон на исправленном инструменте

    466 пакетов: находок 0, чистых 445, помечено самим компилятором 6, пропущено 15

**Ноль ложных срабатываний на 466 реальных программах.**

Шесть программ, помеченных самим компилятором, из подсчёта точности исключены
корректно: о них автор уже предупреждён, и повторная пометка не является
самостоятельным результатом.

### 13.4 Что это измеряет и чего не измеряет

Измеряет: долю ложных срабатываний на коде, который писали и проверяли люди.
Прежняя оценка (38 из 39 на `compile_success_no_bug`) была получена на выборке в
двенадцать раз меньшей; здесь она подтверждена на порядок большем корпусе и с
нулём ошибок.

Не измеряет: чувствительность. Отсутствие находок в корпусе, который его авторы
считают корректным, — ожидаемый исход, и трактовать его как «дыр нет» нельзя.
Чувствительность оценена отдельно: на восьми построенных случаях (ловятся все
восемь при молчании компилятора) и на размеченной выборке `compile_success_with_bug`
(раздел 12).

### 13.5 Побочный результат: обход чужого корпуса проверяет сам инструмент

Единственная пометка на 466 программах оказалась ошибкой инструмента, а не
находкой. Это стоит зафиксировать как методический приём: прогон по большому
корпусу заведомо корректного кода — не только оценка ложных срабатываний, но и
способ обнаружить дефекты собственного анализатора, которые на порождённых
программах не проявляются.

## 14. Собственные фаззеры Noir как инструмент поиска

### 14.1 Основание

Три ошибки соундности, разобранные в разделе 12, найдены не случайным перебором,
а собственными фаззерами разработчиков компилятора. Разумно воспользоваться теми
же инструментами: они написаны людьми, знающими внутреннее устройство, и
порождают формы, до которых внешний генератор не доходит.

Главный из них — `ast_fuzzer`. Он порождает случайные деревья разбора и
сравнивает результаты РАЗНЫХ стратегий компиляции. Все его цели дифференциальные,
эталон не требуется:

| цель                        | что сличает                                   |
|-----------------------------|-----------------------------------------------|
| `min_vs_full`               | минимальный набор проходов SSA против полного |
| `pass_vs_prev`              | SSA до прохода против SSA после него          |
| `acir_vs_brillig`           | исполнение схемы против исполнения Brillig    |
| `orig_vs_morph`             | программа против равносильно изменённой       |
| `comptime_vs_brillig_direct`| вычислитель времени компиляции против Brillig |

Первые две отвечают ровно на исходный вопрос работы: меняет ли оптимизация смысл
программы.

### 14.2 Препятствие и обход

Штатный запуск (`cargo fuzz run`) требует ночной сборки Rust и `cargo-fuzz`,
которых на машине нет. Обход найден дважды.

Первый: каждая цель — тонкая обёртка над `targets::<имя>::fuzz(&mut Unstructured)`,
поэтому достаточно подавать ей случайные байты в цикле. Написан запускатель
`fuzz/examples/sweep.rs`.

Второй, предпочтительный: у целей есть тестовый стенд на `arbtest` с бюджетом
времени и наращиванием размера входа (4 КБ — 1 МБ), настраиваемый переменной
`NOIR_AST_FUZZER_BUDGET_SECS`. Это поддерживаемый авторами путь, и он сам
управляет размерами.

### 14.3 Эпизод с ошибочным выводом о пустоте, и как он разрешился

Первый запускатель отработал пять целей по 400 итераций и дал ноль расхождений.
Замер времени показал «50 итераций — 0 секунд», и результат был признан ПУСТЫМ и
отброшен.

Вывод оказался неверным. Точный замер с масштабированием:

    200 раундов  —  3543 мс   (17 мс на раунд)
    2000 раундов — 36256 мс   (18 мс на раунд)

Рост линейный, 18 мс — это и есть стоимость компиляции и исполнения программы.
Подвела разрешающая способность измерителя: `date +%s` даёт целые секунды, и
50 раундов (около 0,9 с) отобразились нулём. Результат «5 целей x 400 итераций»
действителен, просто объём мал по сравнению со штатным стендом, успевающим за
свой бюджет около 120 тысяч итераций.

**Уточнённая формулировка правила о пустых прогонах.** Проверять надо не «ноль ли
затраченного времени», а СТОИМОСТЬ ОДНОГО раунда при разных объёмах. Единичный
замер на грани разрешения измерителя вводит в заблуждение в обе стороны: он
одинаково способен выдать пустой прогон за содержательный и содержательный за
пустой.

### 14.4 Углублённая настройка: заход в непокрытую область

В документации их же поля `Config::max_type_depth` содержится прямое указание:

> глубина типов 2 достигает лишь массива кортежей из скаляров, все члены которого
> занимают один уплощённый слот; в генерации ACIR есть отдельная ветвь для
> неоднородных элементов (размеры типов, запасные смещения, предикация
> результата), работающая только когда элемент массива смешивает размеры

По умолчанию глубина равна 3, то есть названная ветвь задета минимально. Написан
собственный прогон (`fuzz/examples/deep.rs`), повторяющий сравнение `min_vs_full`,
но с углублённой настройкой: глубина типов 5, глубина выражений 4, массивы до 8
элементов, кортежи до 5, до 6 функций по 40 операторов.

Обоснование выбора: мелкие формы штатный прогон покрывает плотно, глубокие —
редко, поэтому вероятность сохранившейся ошибки выше именно в глубоких.

### 14.5 Фаззинг свойств боевой библиотеки

`nargo fuzz` — серый фаззер по точкам входа, помеченным `#[fuzz]`, сравнивающий
исполнение схемы с Brillig. Для библиотеки больших чисел написаны три
метаморфных тождества, обязанные выполняться при любых входах:

    (x + y) - y == x        вычитание обращает сложение
    x + y == y + x          сложение переместительно
    x * (y + z) == x*y + x*z   умножение распределительно

Такая проверка ловит два класса сразу: ошибки самой библиотеки и ошибки
компилятора на сложном боевом коде, который случайный генератор дерева не
построит. Первое свойство отработало 900 секунд без находок.
